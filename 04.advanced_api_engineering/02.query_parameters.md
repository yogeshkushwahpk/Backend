# Query Parameters and Dynamic Filtering in Express

## 1. What Are Query Parameters?

**Query Parameters** are optional key-value pairs appended to the end of a URL following a question mark (`?`). Multiple parameters are delimited using ampersands (`&`):

```
GET /api/products?category=laptops&brand=Apple&minPrice=50000
```

In Express.js, query parameters are automatically parsed and made accessible via the **`req.query`** object:

```javascript
app.get("/api/products", (req, res) => {
  console.log(req.query);
  // { category: "laptops", brand: "Apple", minPrice: "50000" }
});
```

---

## 2. Why Do We Need Query Parameters?

While route parameters (`/products/:id`) are mandatory path components designed to locate a specific resource, **query parameters are optional modifiers** used to:
1. **Filter** a collection (e.g. `?category=electronics`).
2. **Sort** the results (e.g. `?sort=desc`).
3. **Paginate** large datasets (e.g. `?page=2&limit=20`).
4. **Search** for terms (e.g. `?search=macbook`).

---

## 3. Real-World Analogy

Imagine shopping in a **clothing store**:
- Entering the men's shoe department is the **Route Path**: `/department/shoes`.
- Asking the store clerk: *"Can you only show me shoes that are Nike, Size 10, and under $100?"* represents the **Query Parameters**:
  `?brand=Nike&size=10&maxPrice=100`.
- The shoes are still in the same department; you are simply narrowing down the view!

---

## 4. Route Parameters vs. Query Parameters

| Feature | Route Parameters (`req.params`) | Query Parameters (`req.query`) |
| :--- | :--- | :--- |
| **URL Syntax** | `/products/:id` | `/products?brand=Apple` |
| **Location** | Integrated within the URL path | After the `?` delimiter |
| **Requirement** | Mandatory for the route to match | Optional; route matches with or without them |
| **Primary Purpose** | Identify a specific unique resource | Filter, sort, paginate, or modify a collection |
| **Code Access** | `req.params.id` | `req.query.brand` |

---

## 5. Building Dynamic MongoDB Queries

In real-world applications, a client might pass `category`, `brand`, both, or neither. If you hardcode `{ category: req.query.category, brand: req.query.brand }`, Mongoose will search for documents where fields equal `undefined`, which matches nothing.

The **Dynamic Filter Pattern** constructs the filter object progressively:

```javascript
app.get("/api/products", async (req, res) => {
  try {
    const { category, brand, minPrice, maxPrice } = req.query;

    // 1. Start with an empty query object
    const filter = {};

    // 2. Add properties ONLY if they were provided in the query string
    if (category) {
      filter.category = category.toLowerCase();
    }

    if (brand) {
      filter.brand = brand.toLowerCase();
    }

    // 3. Numeric range filters
    if (minPrice || maxPrice) {
      filter.price = {};
      if (minPrice) filter.price.$gte = Number(minPrice);
      if (maxPrice) filter.price.$lte = Number(maxPrice);
    }

    // 4. Pass the dynamically constructed filter object to Mongoose
    const products = await Product.find(filter);

    res.status(200).json({
      success: true,
      count: products.length,
      data: products
    });
  } catch (error) {
    res.status(500).json({
      success: false,
      message: "Server error querying products",
      error: error.message
    });
  }
});
```

## 6. Complete Runnable Server Example

Save as `server.js`:

```javascript
const express = require("express");
const mongoose = require("mongoose");

const app = express();
const PORT = 5000;

app.use(express.json());

// 1. Connect to MongoDB
mongoose
  .connect("mongodb://127.0.0.1:27017/backendClassDB")
  .then(() => console.log("MongoDB Connected Successfully"))
  .catch(err => console.error("Database connection error:", err.message));

// 2. Schema and Model
const productSchema = new mongoose.Schema({
  title: { type: String, required: true },
  price: { type: Number, required: true },
  category: { type: String, required: true, lowercase: true },
  brand: { type: String, required: true, lowercase: true }
});

const Product = mongoose.model("Product", productSchema);

// 3. Bulk Seed Route
app.post("/api/products/bulk", async (req, res) => {
  try {
    const inserted = await Product.insertMany(req.body);
    res.status(201).json({
      success: true,
      message: `${inserted.length} products inserted`,
      data: inserted
    });
  } catch (error) {
    res.status(500).json({ success: false, error: error.message });
  }
});

// 4. Dynamic Filter Route using req.query
app.get("/api/products", async (req, res) => {
  try {
    const { category, brand, minPrice, maxPrice } = req.query;

    const filter = {};

    if (category) {
      filter.category = category.toLowerCase();
    }

    if (brand) {
      filter.brand = brand.toLowerCase();
    }

    if (minPrice || maxPrice) {
      filter.price = {};
      if (minPrice) filter.price.$gte = Number(minPrice);
      if (maxPrice) filter.price.$lte = Number(maxPrice);
    }

    const products = await Product.find(filter);

    res.status(200).json({
      success: true,
      appliedFilters: filter,
      count: products.length,
      data: products
    });
  } catch (error) {
    res.status(500).json({
      success: false,
      message: "Server error querying products",
      error: error.message
    });
  }
});

app.listen(PORT, () => {
  console.log(`Server running at http://localhost:${PORT}`);
});
```

## 8. Common Pitfalls to Avoid

| Pitfall | Problem | Solution |
| :--- | :--- | :--- |
| **Forgetting that query params are strings** | `req.query.minPrice` evaluates to `"50000"` (String). Using string comparisons in MongoDB numeric fields yields unexpected behavior. | Cast numeric values explicitly with `Number(req.query.minPrice)`. |
| **Passing `undefined` to Mongoose** | `{ brand: req.query.brand }` when no brand is sent queries `{ brand: undefined }`. | Build the filter conditionally using `if (brand) filter.brand = brand;`. |
| **Case Sensitivity mismatch** | Searching `?category=Laptops` fails if documents store `"laptops"`. | Normalize to lowercase on both insertion and query, or use regex `$options: 'i'`. |
| **Returning 404 on empty query results** | When a search yields no results (`[]`), returning `404 Not Found` implies the endpoint is broken. | Return `200 OK` with an empty array `[]` and `count: 0`. |

## 11. Interview Questions & Model Answers

### Q1: Why are query parameters better suited for filtering than route parameters?
**Answer:**
Route parameters are structural elements of the URI path that identify hierarchical resources (e.g. `/users/123/orders`). Query parameters come after the `?` character and are completely optional. Because client filters vary dynamically (a user may filter by category, brand, price, or nothing at all), query parameters allow a single endpoint (`GET /api/products`) to accept any permutation of filters without requiring dozens of hardcoded route permutations.

### Q2: Why should an empty search or filter query return `200 OK` with `[]` instead of `404 Not Found`?
**Answer:**
In REST semantics, `404 Not Found` means that the requested **route or URI resource itself does not exist** (e.g. the endpoint URL is misspelled). When a client queries a valid collection with filters that happen to match 0 documents, the search operation executed successfully. Returning `200 OK` with an empty array `[]` correctly informs the client that the server functioned properly and that no records match the criteria.
