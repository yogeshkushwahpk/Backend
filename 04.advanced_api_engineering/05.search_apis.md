# Search APIs with MongoDB and Express

## 1. What is a Search API?

A **Search API** allows clients to query datasets using partial, case-insensitive textual keywords.

Unlike exact-match filtering (`{ category: "laptops" }`), a search API returns matches when a user types a fragment or partial term:
- Typing `"sam"` $\to$ matches `"Samsung Galaxy S23"`, `"Samsung 4K TV"`
- Typing `"lap"` $\to$ matches `"Dell Laptop"`, `"MacBook Pro Laptop"`

MongoDB provides the **`$regex`** operator to evaluate regular expressions directly inside query documents.

---

## 2. Why Do We Need Search APIs?

Real-world users rarely know the exact, complete, case-sensitive title of a product or user record.

Search APIs provide:
1. **User Discovery**: Instant auto-suggest, autocomplete, and search-as-you-type bars.
2. **Multi-Field Matching**: Allowing a single search box to match across product titles, descriptions, categories, and brand names simultaneously.
3. **Resilience**: Case-insensitive matching so `"apple"`, `"Apple"`, and `"APPLE"` all return the same results.

---

## 3. Real-World Analogy

Imagine searching for a book in a **library catalog**:
- **Exact Match**: You must type the exact title *"To Kill a Mockingbird"* without typo or difference in capitalization.
- **Search API (`$regex`)**: You type *"mocking"*, and the system searches across the title, description, and author fields to return the book instantly.

## 4. Core Concepts: `$regex` and `$or`

### 4.1 The `$regex` Operator
The `$regex` operator provides regular expression capabilities for pattern matching strings in queries:

```javascript
{ title: { $regex: "phone", $options: "i" } }
```

| Component | Meaning |
| :--- | :--- |
| **`$regex: "phone"`** | Matches any document where `title` **contains** the substring `"phone"`. |
| **`$options: "i"`** | Case-insensitive flag. Matches `"Phone"`, `"PHONE"`, `"phone"`, or `"PhOnE"`. |

### 4.2 Exact Match vs. Regex Search
```javascript
// 1. Exact Match: Only matches "Phone" exactly
Product.find({ title: "Phone" });

// 2. Partial Substring Regex: Matches "iPhone 15", "Smartphone", "Headphones"
Product.find({ title: { $regex: "phone", $options: "i" } });
```

### 4.3 Multi-Field Search with the `$or` Operator
To allow a single search keyword to scan across multiple fields (e.g. `title`, `brand`, and `category`), use MongoDB's logical **`$or`** operator:

```javascript
Product.find({
  $or: [
    { title:    { $regex: searchTerm, $options: "i" } },
    { brand:    { $regex: searchTerm, $options: "i" } },
    { category: { $regex: searchTerm, $options: "i" } }
  ]
});
```

## 5. Implementation Guide

### 5.1 Escaping Regex Special Characters
If a user searches for special characters like `?`, `+`, `(`, or `*`, passing raw input directly to `$regex` can cause regular expression syntax errors or ReDoS (Regular Expression Denial of Service). Always escape regex characters:

```javascript
const escapeRegex = (text) => {
  return text.replace(/[-[\]{}()*+?.,\\^$|#\s]/g, "\\$&");
};
```

---

### 5.2 The Master Route: Search + Filter + Sort + Pagination

Here is the production standard endpoint combining all advanced API concepts into a single unified handler:

```javascript
app.get("/api/products", async (req, res) => {
  try {
    const { search, category, brand, sort, page = 1, limit = 10 } = req.query;

    // 1. Base Query Filter
    const filter = {};

    // 2. Category & Brand Exact Filtering
    if (category) filter.category = category.toLowerCase();
    if (brand) filter.brand = brand.toLowerCase();

    // 3. Multi-Field Search with $or and $regex
    if (search) {
      const sanitizedSearch = escapeRegex(search.trim());
      const searchRegex = { $regex: sanitizedSearch, $options: "i" };

      filter.$or = [
        { title: searchRegex },
        { brand: searchRegex },
        { category: searchRegex }
      ];
    }

    // 4. Sorting Logic
    const sortCriteria = {};
    if (sort === "asc") {
      sortCriteria.price = 1;
    } else if (sort === "desc") {
      sortCriteria.price = -1;
    } else {
      sortCriteria.createdAt = -1; // Default: newest first
    }

    // 5. Pagination Calculation
    const pageNumber = Math.max(1, parseInt(page, 10) || 1);
    const limitNumber = Math.min(100, Math.max(1, parseInt(limit, 10) || 10));
    const skip = (pageNumber - 1) * limitNumber;

    // 6. Parallel Execution
    const [products, totalDocuments] = await Promise.all([
      Product.find(filter)
        .sort(sortCriteria)
        .skip(skip)
        .limit(limitNumber),
      Product.countDocuments(filter)
    ]);

    const totalPages = Math.ceil(totalDocuments / limitNumber);

    // 7. Response Envelope with 200 OK
    res.status(200).json({
      success: true,
      pagination: {
        totalDocuments,
        totalPages,
        currentPage: pageNumber,
        limit: limitNumber,
        hasNextPage: pageNumber < totalPages,
        hasPrevPage: pageNumber > 1
      },
      data: products
    });
  } catch (error) {
    res.status(500).json({
      success: false,
      message: "Server error querying products",
      error: error.message
    });
  }
});
```

## 6. Complete Runnable Server Example

Save as `server.js`:

```javascript
const express = require("express");
const mongoose = require("mongoose");

const app = express();
const PORT = 5000;

app.use(express.json());

// 1. Connect to MongoDB
mongoose
  .connect("mongodb://127.0.0.1:27017/backendClassDB")
  .then(() => console.log("MongoDB Connected Successfully"))
  .catch(err => console.error("Database connection error:", err.message));

// 2. Schema and Model
const productSchema = new mongoose.Schema(
  {
    title: { type: String, required: true },
    price: { type: Number, required: true },
    category: { type: String, required: true, lowercase: true },
    brand: { type: String, required: true, lowercase: true }
  },
  { timestamps: true }
);

const Product = mongoose.model("Product", productSchema);

// Helper function to escape regex characters safely
const escapeRegex = (text) => text.replace(/[-[\]{}()*+?.,\\^$|#\s]/g, "\\$&");

// 3. Bulk Seed Route
app.post("/api/products/bulk", async (req, res) => {
  try {
    const inserted = await Product.insertMany(req.body);
    res.status(201).json({
      success: true,
      message: `${inserted.length} products inserted`,
      data: inserted
    });
  } catch (error) {
    res.status(500).json({ success: false, error: error.message });
  }
});

// 4. Standalone Multi-Field Search Endpoint
app.get("/api/products/search", async (req, res) => {
  try {
    const { q } = req.query;

    if (!q) {
      return res.status(400).json({
        success: false,
        message: "Please provide a search term (?q=keyword)"
      });
    }

    const regex = { $regex: escapeRegex(q), $options: "i" };

    const products = await Product.find({
      $or: [{ title: regex }, { brand: regex }, { category: regex }]
    });

    res.status(200).json({
      success: true,
      count: products.length,
      searchTerm: q,
      data: products
    });
  } catch (error) {
    res.status(500).json({
      success: false,
      message: "Server error during search",
      error: error.message
    });
  }
});

// 5. Master Route (Search + Filter + Sort + Pagination)
app.get("/api/products", async (req, res) => {
  try {
    const { search, category, brand, sort, page = 1, limit = 10 } = req.query;

    const filter = {};

    if (category) filter.category = category.toLowerCase();
    if (brand) filter.brand = brand.toLowerCase();

    if (search) {
      const regex = { $regex: escapeRegex(search), $options: "i" };
      filter.$or = [{ title: regex }, { brand: regex }, { category: regex }];
    }

    const sortOption = {};
    if (sort === "asc") sortOption.price = 1;
    if (sort === "desc") sortOption.price = -1;

    const pageNum = Math.max(1, parseInt(page, 10) || 1);
    const limitNum = Math.min(100, Math.max(1, parseInt(limit, 10) || 10));
    const skip = (pageNum - 1) * limitNum;

    const [products, totalDocuments] = await Promise.all([
      Product.find(filter).sort(sortOption).skip(skip).limit(limitNum),
      Product.countDocuments(filter)
    ]);

    res.status(200).json({
      success: true,
      pagination: {
        totalDocuments,
        totalPages: Math.ceil(totalDocuments / limitNum),
        currentPage: pageNum,
        limit: limitNum
      },
      data: products
    });
  } catch (error) {
    res.status(500).json({
      success: false,
      message: "Server error querying products",
      error: error.message
    });
  }
});

app.listen(PORT, () => {
  console.log(`Server listening on http://localhost:${PORT}`);
});
```

## 8. Common Mistakes to Avoid

| Mistake | Consequence | Correct Approach |
| :--- | :--- | :--- |
| **Returning HTTP `201 Created` for search** | Misleads client developers that a resource was created. | Always return `200 OK` for search results. |
| **Returning 401 or 404 in `catch` blocks** | HTTP 401 means Unauthorized. A query syntax error is an internal server error. | Always return `500 Internal Server Error` in `catch (error)` handlers. |
| **Omitting regex sanitization** | Searching for `?q=(abc` crashes Node.js with `SyntaxError: Invalid regular expression`. | Escape special characters using `escapeRegex()`. |
| **Using unindexed `$regex` on large text bodies** | Leading wildcard queries (`/.*term.*/`) force a full collection scan (COLLSCAN). | For production full-text search across large articles, use MongoDB **Text Indexes** (`$text: { $search: ... }`). |

---

## 9. Regex Search vs. MongoDB Text Search (`$text`)

| Feature | Regex Search (`$regex`) | MongoDB Text Index (`$text`) |
| :--- | :--- | :--- |
| **Index Used** | Standard B-Tree index (inefficient for leading wildcards) | Specialized Inverted Text Index |
| **Stemming & Stopwords** | None (matches raw characters) | Language-aware stemming ("runs" matches "running") |
| **Relevance Scoring** | None | Assigns relevance score (`textScore`) |
| **Partial Match** | Substring matches (`"mac"` matches `"MacBook"`) | Matches whole words or phrases |
| **Best For** | Short fields (titles, usernames, brand names) | Long bodies of text (blog posts, articles, documentation) |

## 12. Interview Questions & Model Answers

### Q1: What are the performance implications of using `$regex` with leading wildcards in MongoDB?
**Answer:**
When a regular expression search does not start with an anchor (such as `^term`), MongoDB cannot leverage standard B-Tree index prefix matching. It must execute a **full collection scan (COLLSCAN)**, reading every single document from disk and evaluating the regex string against each one in CPU memory. On large collections, this results in significant latency and high CPU utilization. For high-volume production full-text search, developers should implement MongoDB Text Indexes or dedicated search engines like Elasticsearch or Algolia.

### Q2: How does the `$or` operator differ from `$and` in MongoDB queries?
**Answer:**
In MongoDB, multiple top-level keys in a query object are implicitly joined with logical **AND** (e.g. `{ category: "audio", brand: "sony" }` requires both conditions to be satisfied). The **`$or`** operator takes an array of sub-query objects and evaluates to `true` if **at least one** condition in the array matches. It is essential for multi-field search interfaces where a single query term might appear in either the `title`, `brand`, or `description`.
