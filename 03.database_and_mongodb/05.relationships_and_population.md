# MongoDB Relationships and Mongoose Population

## Connect Documents Without Losing Control of Query Cost

---

## 1. References connect independent documents

Use an `ObjectId` reference when data has its own collection and lifecycle.

```js
const postSchema = new mongoose.Schema({
  title: { type: String, required: true },
  body: { type: String, required: true },
  author: {
    type: mongoose.Schema.Types.ObjectId,
    ref: 'User',
    required: true,
  },
});
```

The `author` field stores only a User `_id`. The `ref` tells Mongoose which model to use if we later populate it.

## 2. Populate only what a response needs

```js
const post = await Post.findById(postId).populate('author', 'name email');
```

This replaces the `author` id in the returned document with the selected User fields. Never populate sensitive fields such as password hashes, tokens, or internal flags.

Populate nested data carefully:

```js
const orders = await Order.find({ customer: userId })
  .populate('items.product', 'name price category')
  .limit(20)
  .lean();
```

## 3. One-to-many relationships

For a User and many Posts, put the user reference on the many side:

```text
User 1  <---  many Post documents
```

Each Post stores `author`. Do not store every post id in a User array if the list can grow indefinitely.

To find the user’s posts, query the posts collection:

```js
const posts = await Post.find({ author: userId }).sort({ createdAt: -1 });
```

## 4. Virtual populate

Virtual populate gives a User a convenient `posts` property without storing a growing array of post ids.

```js
userSchema.virtual('posts', {
  ref: 'Post',
  localField: '_id',
  foreignField: 'author',
});

const user = await User.findById(userId).populate('posts', 'title createdAt');
```

Enable virtuals in `toJSON` if you need them in API responses.

## 5. When not to populate

Population is convenient, but it can make a response slow or unexpectedly large. Avoid it when:

- You only need the referenced id.
- You are returning a long list of documents.
- The relationship has an unbounded number of children.
- A reporting query is better expressed with an aggregation pipeline.

Set field selections and limits. Measure real queries before adding nested population.

## 6. Keep consistency when data changes

If an Order stores a product name and price snapshot, do not try to update old orders when the Product changes. The snapshot represents history.

If two independent documents must either both change or both remain unchanged, use a transaction. The final database lesson introduces that pattern.

2. A teacher response with the latest five courses using virtual populate.
3. A route that lists courses without population when only teacher ids are needed.
