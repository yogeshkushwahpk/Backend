# MongoDB Data Modelling and Schema Design

## Design Documents Before You Write Controllers

---

## 1. Start with questions, not collections

Before creating a schema, write down:

1. What does one record represent?
2. Which fields are required?
3. Which data is read together most often?
4. Can one record grow without limit?
5. Is the relationship one-to-one, one-to-many, or many-to-many?

MongoDB stores documents, not rows. A good document contains data that belongs together and is usually read together.

## 2. A practical example

An e-commerce API may need users, products, and orders.

```text
User     -> name, email, address
Product  -> name, price, category, stock
Order    -> customer, items, deliveryAddress, total, status
```

An order should keep a snapshot of the product name and price at purchase time. If a product price changes later, an old order should still show the price the customer paid.

## 3. Embed or reference?

MongoDB gives two main ways to model related data.

| Choose embedding when... | Choose a reference when... |
| --- | --- |
| Data belongs only to one parent document. | Data has its own lifecycle. |
| The child list stays small and bounded. | Many documents share the same data. |
| You normally read it with the parent. | The related collection can grow large. |
| You want one read to return the complete data. | You need to query the related data independently. |

### Embedded document

An address belongs closely to one user and is normally read with that user.

```js
const userSchema = new mongoose.Schema({
  name: { type: String, required: true },
  addresses: [
    {
      line1: String,
      city: String,
      postalCode: String,
    },
  ],
});
```

### Referenced document

A product exists independently and can appear in many orders. Store its `_id` in each order item.

```js
const orderSchema = new mongoose.Schema({
  customer: {
    type: mongoose.Schema.Types.ObjectId,
    ref: 'User',
    required: true,
  },
  items: [
    {
      product: {
        type: mongoose.Schema.Types.ObjectId,
        ref: 'Product',
        required: true,
      },
      name: { type: String, required: true },
      priceAtPurchase: { type: Number, required: true, min: 0 },
      quantity: { type: Number, required: true, min: 1 },
    },
  ],
});
```

## 4. Avoid unbounded arrays

Do not put every order a customer has ever made inside the User document. That array can grow forever and makes one document too large. Create an `orders` collection that references the user instead.

The same rule applies to messages, comments, notifications, activity logs, and audit history.

## 5. Use Mongoose schemas to protect data quality

Schemas define expected fields and rules.

```js
const productSchema = new mongoose.Schema(
  {
    name: { type: String, required: true, trim: true },
    price: { type: Number, required: true, min: 0 },
    category: { type: String, required: true, index: true },
    inStock: { type: Boolean, default: true },
  },
  { timestamps: true }
);
```

`timestamps: true` adds `createdAt` and `updatedAt`. These fields are useful in almost every backend application.

## 6. Design for the queries you will make

Data modelling and query design are connected. If the main screen lists products by category and price, expect an index for that pattern later. If the main screen shows an order with its items, keep order-item details together.

Do not create collections solely because a SQL database would use separate tables. Let the application’s read and write patterns guide the design.

## 7. A modelling checklist

- Give each collection one clear responsibility.
- Make required business fields required in the schema.
- Embed small, bounded data that is read with its parent.
- Reference large, shared, or independently queried data.
- Store historical snapshots when past values must not change.
- Add timestamps.
- Plan indexes from real query patterns, not guesses.

## Practice

Model a blog application with `User`, `Post`, and `Comment`. Decide which fields should be embedded and which should be references. Explain how you will prevent a post document from growing forever.
