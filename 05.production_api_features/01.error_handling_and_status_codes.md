# Error Handling and HTTP Status Codes in Express

## 1. What is Error Handling?

**Error Handling** is the programmatic process of intercepting, processing, and responding to exceptional conditions that occur during the execution of an API request.

Professional error handling ensures:
- The Node.js server **never crashes unexpectedly**.
- The client **always receives a predictable, structured response** explaining what went wrong.
- The **correct HTTP status code** (`400`, `401`, `403`, `404`, `429`, `500`) is returned.
- Sensitive server stack traces or database connection credentials are **never leaked to the client**.

---

## 2. The Three Primary Buckets of API Errors

Errors are categorized by who was responsible:

### 1. `400 Bad Request` (The Client Messed Up)
The client sent invalid, malformed, or missing parameters that the server cannot process.
- **Analogy**: Putting letters into an ATM numeric PIN pad.
- **Examples**: Missing required `email`, sending `"twenty"` for an `age` field, or sending invalid JSON syntax.
- **Action**: Return `400` with an explicit list of field validation errors.

### 2. `404 Not Found` (The Resource Does Not Exist)
The client sent a valid request, but the server has no record matching that URI or ID.
- **Analogy**: Looking for a specific book on a library shelf when someone checked it out.
- **Examples**: Querying `GET /users/650c8...` when that `_id` is absent from MongoDB, or hitting an unmapped URL `/random-route`.
- **Action**: Return `404` with `"User not found"` or `"Endpoint not found"`.

### 3. `500 Internal Server Error` (The Server Broke)
The client's request was completely valid, but an unhandled exception or infrastructural failure occurred on the server.
- **Analogy**: You ordered food cleanly from a restaurant menu, but the kitchen stove caught fire.
- **Examples**: Database connection dropped, third-party payment gateway timed out, or unhandled null-pointer runtime error.
- **Action**: Log the full technical error internally for developers, but return a sanitized `500` error to the client.

> [!NOTE]
> **Authentication Status Codes:**
> - `401 Unauthorized`: "You must log in to access this resource (missing or invalid token)."
> - `403 Forbidden`: "You are logged in, but you lack permission to perform this action (e.g. non-admin accessing admin portal)."

## 3. Express 4-Parameter Global Error Middleware

Express identifies error-handling middleware by checking its function arity (number of declared arguments). An error handler **must take exactly four parameters**:

```javascript
// (err, req, res, next)
const errorHandler = (err, req, res, next) => {
  console.error("Global Error Intercepted:", err.stack);

  const statusCode = err.statusCode || (res.statusCode === 200 ? 500 : res.statusCode);

  res.status(statusCode).json({
    success: false,
    message: err.message || "Internal Server Error",
    stack: process.env.NODE_ENV === "production" ? null : err.stack
  });
};
```

## 5. Complete Runnable Code Example

### Step 1: Custom Error Class (`src/utils/AppError.js`)
```javascript
class AppError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.statusCode = statusCode;
    this.status = `${statusCode}`.startsWith("4") ? "fail" : "error";
    this.isOperational = true; // Distinguishes known operational bugs from programming bugs

    Error.captureStackTrace(this, this.constructor);
  }
}

module.exports = AppError;
```

---

### Step 2: Global Error Middleware (`src/middlewares/errorHandler.js`)
```javascript
const errorHandler = (err, req, res, next) => {
  const statusCode = err.statusCode || 500;

  // Log error details for server operators
  console.error(`[ERROR] ${new Date().toISOString()} | ${req.method} ${req.originalUrl} | Status: ${statusCode}`);
  console.error(err.stack);

  res.status(statusCode).json({
    success: false,
    message: err.message || "Internal Server Error",
    // Only expose stack traces during local development
    ...(process.env.NODE_ENV !== "production" && { stack: err.stack })
  });
};

module.exports = errorHandler;
```

---

### Step 3: Controller Functions (`src/controllers/user.controller.js`)
```javascript
const User = require("../models/user.model");
const mongoose = require("mongoose");
const AppError = require("../utils/AppError");

// GET /api/users
const getAllUsers = async (req, res, next) => {
  try {
    const users = await User.find();
    res.status(200).json({ success: true, count: users.length, data: users });
  } catch (error) {
    next(error); // Passes error forward to global error handler
  }
};

// GET /api/users/:id
const getUserById = async (req, res, next) => {
  try {
    const { id } = req.params;

    if (!mongoose.Types.ObjectId.isValid(id)) {
      return next(new AppError(`Invalid ObjectId format: '${id}'`, 400));
    }

    const user = await User.findById(id);

    if (!user) {
      return next(new AppError(`User with ID ${id} not found`, 404));
    }

    res.status(200).json({ success: true, data: user });
  } catch (error) {
    next(error);
  }
};

// POST /api/users
const createUser = async (req, res, next) => {
  try {
    const { name, email } = req.body;

    if (!name || !email) {
      return next(new AppError("Both 'name' and 'email' are required fields", 400));
    }

    const user = await User.create({ name, email });
    res.status(201).json({ success: true, data: user });
  } catch (error) {
    next(error);
  }
};

module.exports = { getAllUsers, getUserById, createUser };
```

### Step 4: Wire Everything in Express (`src/app.js`)
```javascript
const express = require("express");
const userRoutes = require("./routes/user.routes");
const errorHandler = require("./middlewares/errorHandler");
const AppError = require("./utils/AppError");

const app = express();
app.use(express.json());

// Routes
app.use("/api/users", userRoutes);

// Catch-All for Unhandled Routes (Must be registered AFTER all routes)
app.use("*", (req, res, next) => {
  next(new AppError(`Route ${req.method} ${req.originalUrl} does not exist`, 404));
});

// Global Error Handler (MUST BE THE VERY LAST MIDDLEWARE)
app.use(errorHandler);

module.exports = app;
```

## 7. Common Mistakes to Avoid

| Mistake | Consequence | Correct Approach |
| :--- | :--- | :--- |
| **Declaring error handler with only 3 params `(err, req, res)`** | Express treats it as a standard request middleware and skips it during error cascades. | Must declare all 4 parameters `(err, req, res, next)` even if `next` is unused. |
| **Placing `app.use(errorHandler)` before routes** | Any errors thrown inside routes will never reach the error handler. | Mount error middleware at the absolute bottom of `app.js`. |
| **Leaking raw database stack traces in production** | Attackers learn internal table schemas, directory structures, and library versions. | Strip `err.stack` when `NODE_ENV === "production"`. |
| **Using `res.status(404).send(err)` in `catch` blocks** | Masks server errors as missing routes and confuses debugging. | Reserve `404` for unfound entities; use `500` for caught exceptions. |

## 11. Interview Questions & Model Answers

### Q1: How does Express recognize that a middleware function is an error handler?
**Answer:**
JavaScript functions have a `.length` property that reports the number of arguments declared in their signature. Standard Express middleware expects 3 parameters `(req, res, next)`. When an error is passed to `next(err)` or thrown, Express scans the internal router stack specifically looking for middleware functions with `fn.length === 4`, corresponding to `(err, req, res, next)`. If only 3 parameters are declared, Express treats it as a standard request handler and bypasses it during error routing.

### Q2: What are "Operational Errors" versus "Programmer Errors"?
**Answer:**
- **Operational Errors** are known, anticipated runtime failures that occur in properly written applications (e.g. invalid user input, expired JWT, resource not found, database connection timeout). These should be caught cleanly and answered with meaningful HTTP status codes (400, 401, 404, 503).
- **Programmer Errors** are bugs in the codebase itself (e.g. syntax errors, referencing undefined variables, calling a method on null). These should be caught by global exception handlers, logged to telemetry, and returned to clients as a generic `500 Internal Server Error`.
