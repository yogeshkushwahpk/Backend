# Understanding RESTful APIs

## Architectural Principles, HTTP Verbs, and API Design Contracts

---

## 1. Why REST Matters in Backend Development

Once a server is capable of receiving network connections and returning data, a critical architectural challenge arises:

> **How should APIs be designed so that different frontend clients (web apps, mobile devices, third-party services) can communicate with the backend consistently, predictably, and reliably?**

Without a standardized design contract, backend APIs become chaotic:
* One developer creates `/getAllUsers`
* Another creates `/fetch-user-list`
* A third creates `/user_read_all`

**REST (Representational State Transfer)** provides the industry-standard design conventions for building clean, maintainable, and scalable web APIs.

REST is **not a programming language**, **not a library**, and **not a framework**. It is an **architectural style** that defines how resources should be identified and manipulated using the existing capabilities of the HTTP protocol.

---

## 2. What is REST?

**REST** stands for **Representational State Transfer**, introduced in 2000 by computer scientist Roy Fielding in his doctoral dissertation.

In practical backend terms:
1. The server manages and exposes **Resources** (data entities such as users, orders, products).
2. Every resource is identified by a clean, unique **URL**.
3. Clients perform operations on these resources using standard **HTTP Methods (Verbs)**.
4. The server returns a **Representation** of the resource's current state (most commonly formatted as **JSON**).
5. All interactions are strictly **Stateless**.

## 3. Resources: The Core Concept of REST

![REST API Model Diagram](https://kajabi-storefronts-production.kajabi-cdn.com/kajabi-storefronts-production/file-uploads/blogs/2147485434/images/315487-7af3-d17-c8af-0b4d8af188db_rest-api-model-diagram.png)

![How to Design a REST API](https://restfulapi.net/wp-content/uploads/How-to-Design-a-REST-API.png)

In REST, everything is modeled around **Resources**. A resource is any conceptual object managed by your system.

### Golden Rule of RESTful URL Design:
> **URLs should be NOUNS (things), NEVER VERBS (actions).**

The HTTP Method tells the server **what action to perform**; the URL tells the server **which resource to act upon**.

| Action Description | ❌ Bad URL Design (RPC Style / Verbs in URL) | ✅ Proper RESTful URL Design |
| :--- | :--- | :--- |
| Get all students | `GET /getAllStudents` | `GET /students` |
| Get student with ID 10 | `GET /getStudentById?id=10` | `GET /students/10` |
| Create new student | `POST /createNewStudent` | `POST /students` |
| Update student #10 | `POST /updateStudent/10` | `PUT /students/10` or `PATCH /students/10` |
| Delete student #10 | `GET /deleteStudent?id=10` (Dangerous!) | `DELETE /students/10` |

### Nested Resources:
When resources have hierarchical relationships (e.g. reviews belonging to a product):
* `GET /products/45/reviews` — Get all reviews for product 45.
* `POST /products/45/reviews` — Add a new review to product 45.

## 4. HTTP Methods and Their Meaning in REST

![HTTP Methods](https://www.techtarget.com/rms/onlineimages/http_methods_purpose_and_properties-f_mobile.png)

![HTTP Methods overview](https://media.licdn.com/dms/image/v2/D4D12AQHxG4Prn4ZrBQ/article-cover_image-shrink_600_2000/article-cover_image-shrink_600_2000/0/1718998421506?e=2147483647&t=-2LQBR1-lDFdKqTy66DNfGm4cTz7xy27k8-QYYsYaio&v=beta)

In RESTful design, **the exact same URL behaves differently based on the HTTP verb used**:

```
GET    /users   → Fetch all users
POST   /users   → Create a new user
GET    /users/5 → Fetch user with ID 5
PUT    /users/5 → Replace user with ID 5
PATCH  /users/5 → Update part of user with ID 5
DELETE /users/5 → Remove user with ID 5
```

---

### 4.1 GET — Retrieve Data (Read-Only)

* **Purpose:** Fetch a list of resources or a single resource without altering server state.
* **Safe:** Yes (Calling GET a million times modifies zero data on the server).
* **Idempotent:** Yes (Making multiple identical GET requests produces the same result).
* **Request Body:** Never used in standard GET requests.
* **Cacheable:** Yes (Browsers, CDNs, and proxies can cache GET responses).

```http
GET /users/101 HTTP/1.1
Host: api.example.com
```

> **⚠️ Critical Safety Rule:**
> Never use GET to delete or mutate data (e.g. `GET /users/delete?id=5`). Web crawlers (like Googlebot) follow links automatically and would accidentally delete your entire database!

---

### 4.2 POST — Create a New Resource

* **Purpose:** Submit data to the server to create a **brand new resource**.
* **Safe:** No (Changes server database state).
* **Idempotent:** No (Sending the same POST request 3 times creates 3 duplicate records).
* **Request Body:** Contains the data for the new entity (JSON format).
* **Success Status Code:** `201 Created`.

```http
POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "name": "Aditya Sharma",
  "email": "aditya@example.com",
  "role": "student"
}
```

---

### 4.3 PUT — Full Replacement of a Resource

* **Purpose:** Replace the **entire existing representation** of a resource.
* **Safe:** No.
* **Idempotent:** Yes (Replacing user 101 with the exact same object multiple times leaves the user in the exact same state).
* **Behavior on Missing Fields:** If you omit a field in a PUT payload, that field is reset or erased in the database.

```http
PUT /users/101 HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "name": "Aditya Sharma",
  "email": "new_email@example.com",
  "role": "student"
}
```

---

### 4.4 PATCH — Partial Modification of a Resource

* **Purpose:** Update **only the specific fields** supplied in the request body, leaving all other fields untouched.
* **Safe:** No.
* **Idempotent:** Not guaranteed by definition, but in practice usually implemented idempotently for field updates.
* **Use Case:** Changing a user's password, updating an email, toggling a checkbox (`isPinned: true`).

```http
PATCH /users/101 HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "isPinned": true
}
```
*(Notice: Only `isPinned` changes. The user's name, email, and other fields remain unchanged.)*

---

### 4.5 PUT vs PATCH: The Definitive Difference

| Feature / Behavior | `PUT` (Full Replacement) | `PATCH` (Partial Update) |
| :--- | :--- | :--- |
| **Concept** | Replace the whole document | Modify only specified fields |
| **Omitted Fields** | Overwritten / deleted / set to default | Remain completely unchanged |
| **Payload Size** | Full object required | Only changed fields sent |
| **Real-World Use** | Submitting a complete user profile form | Toggling status, changing password, updating single field |

---

### 4.6 DELETE — Remove a Resource

* **Purpose:** Delete a resource permanently from the server.
* **Safe:** No (Destroys data).
* **Idempotent:** Yes (Deleting resource 101 once deletes it. Deleting it again still results in resource 101 being gone).
* **Request Body:** Not typically used.
* **Success Status Codes:** `200 OK` (with confirmation message) or `204 No Content` (empty response body).

```http
DELETE /users/101 HTTP/1.1
Host: api.example.com
```

---

### 4.7 HEAD & OPTIONS

* **HEAD:** Exactly identical to GET, but the server returns **only headers without any response body**. Used by browsers and CDNs to check file size (`Content-Length`) or modification date without downloading the payload.
* **OPTIONS:** Asks the server: *"Which HTTP methods and headers are permitted on this URL?"* Used automatically by browsers for **CORS preflight checks** before sending non-simple requests.

---

### 4.8 Summary Reference Table of HTTP Verbs

| Method | Meaning in REST | Safe? | Idempotent? | Request Body? | Standard Response Status |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **GET** | Read resource(s) | **Yes** | **Yes** | No | `200 OK` |
| **POST** | Create new resource | No | No | **Yes** | `201 Created` |
| **PUT** | Replace entire resource | No | **Yes** | **Yes** | `200 OK` |
| **PATCH** | Partial update of fields | No | Varies | **Yes** | `200 OK` |
| **DELETE** | Remove resource | No | **Yes** | No | `200 OK` or `204 No Content` |
| **HEAD** | Metadata (headers only) | **Yes** | **Yes** | No | `200 OK` (No body) |
| **OPTIONS** | Check allowed methods | **Yes** | **Yes** | No | `200 OK` / `204 No Content` |

## 5. Statelessness in REST

One of the most essential architectural constraints of REST is **Statelessness**:

> **The server must not store any client session context between requests.**
> Every single HTTP request must contain all the information necessary for the server to understand and authorize it.

### What Statelessness Looks Like:
* In a stateful system: The server stores "User 5 is logged in on Server A" in its RAM. If the user's next request hits Server B, Server B has no idea who the user is!
* In a stateless REST system: The client sends a cryptographically signed token (like a **JWT**) in the `Authorization: Bearer <token>` header on **every single request**. Any server in a cluster of 500 servers can independently verify the token without sharing session memory.

### Benefits of Statelessness:
* **Effortless Horizontal Scaling:** You can add 100 new servers behind a load balancer without worrying about session synchronization.
* **Reliability:** If one server crashes, the user can immediately talk to another server with zero loss of session.

## 6. HTTP Status Codes: The API Contract

![HTTP Status Codes](https://restfulapi.net/wp-content/uploads/HTTP-Error-Codes.jpg)

![Status Codes Categories](https://cdn.prod.website-files.com/62796ab9647626cbab663f42/671124657e500c1aa0737fe2_6711242c69ef42275511fbb9_API%2520response%2520code%2520categories%2520%284%29.webp)

Status codes tell client applications **what happened** before they even parse the response body:

* **`2xx` Success:** The action was understood and accepted.
  * `200 OK` — Standard success for GET, PUT, PATCH, DELETE.
  * `201 Created` — Resource successfully created via POST.
  * `204 No Content` — Action succeeded, but no data is returned in the body (common for DELETE).
* **`3xx` Redirection:** Further action is needed to fulfill the request.
  * `301 Moved Permanently` / `304 Not Modified` (caching).
* **`4xx` Client Error:** The client sent invalid data or violated rules.
  * `400 Bad Request` — Missing fields, validation failure, malformed JSON.
  * `401 Unauthorized` — Authentication missing or invalid token.
  * `403 Forbidden` — Authenticated, but lacks permission (e.g. non-admin accessing admin route).
  * `404 Not Found` — Resource or URL does not exist.
  * `429 Too Many Requests` — Rate limit exceeded.
* **`5xx` Server Error:** The client sent a valid request, but the server broke.
  * `500 Internal Server Error` — Unhandled exception, database crash, bug in code.
  * `502 Bad Gateway` / `503 Service Unavailable`.

## 7. Raw HTTP Implementation of REST Endpoints

To see REST principles in action before moving to Express, here is how a RESTful resource (`/users`) is implemented in raw Node.js:

```js
const http = require("http");

let users = [
  { id: 1, name: "Aarav", role: "student" },
  { id: 2, name: "Priya", role: "mentor" }
];

const server = http.createServer((req, res) => {
  const { method, url } = req;

  // 1. GET /users — Retrieve all users
  if (method === "GET" && url === "/users") {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify(users));
  }

  // 2. POST /users — Create a new user
  else if (method === "POST" && url === "/users") {
    let body = "";
    req.on("data", chunk => { body += chunk; });
    req.on("end", () => {
      const data = JSON.parse(body);
      const newUser = { id: users.length + 1, ...data };
      users.push(newUser);

      res.writeHead(201, { "Content-Type": "application/json" });
      res.end(JSON.stringify({ message: "User created", user: newUser }));
    });
  }

  // 3. Fallback — Unknown route
  else {
    res.writeHead(404, { "Content-Type": "application/json" });
    res.end(JSON.stringify({ error: "Resource not found" }));
  }
});

server.listen(3000, () => {
  console.log("REST API running on port 3000");
});
```

## 8. Common Beginner Mistakes

1. **Using Verbs in URLs:**
   * Writing `/deleteUser/1` instead of `DELETE /users/1`.
2. **Returning `200 OK` for Everything:**
   * Returning status 200 with `{ status: "error", message: "User not found" }` is an anti-pattern! Clients rely on HTTP status codes like `404` or `400` to trigger frontend error handlers.
3. **Using `201 Created` for GET Requests:**
   * Status `201` is strictly for creating new resources on POST. GET requests should return `200 OK`.
4. **Confusing Authentication (`401`) with Authorization (`403`):**
   * `401` means *"I don't know who you are (log in first)"*. `403` means *"I know who you are, but you are not allowed in"*.

---

## 9. Summary & Key Takeaways

* REST is an architectural style designed around **resources** identified by URLs.
* URLs represent **nouns**; HTTP methods represent **actions**.
* `GET` reads, `POST` creates, `PUT` replaces, `PATCH` modifies, `DELETE` removes.
* `PUT` replaces the entire record; `PATCH` updates only the specified fields.
* RESTful services are **stateless**, making them easily scalable across multiple servers.
* HTTP status codes are an essential part of the API contract with frontend consumers.

## 10. Interview Questions

**Q1: What does "Idempotency" mean in REST APIs?**
*Answer:* An HTTP method is idempotent if making multiple identical requests has the same effect on server state as making a single request. `GET`, `PUT`, `DELETE`, `HEAD`, and `OPTIONS` are idempotent. `POST` is not idempotent because repeating it creates multiple duplicate resources.

**Q2: What is the difference between `PUT` and `PATCH`?**
*Answer:* `PUT` is used for full replacement of a resource; any fields omitted from the request body are typically overwritten or set to null/default. `PATCH` is used for partial updates; only the provided fields are modified, and all other fields remain unchanged.

**Q3: Why is statelessness critical for RESTful APIs?**
*Answer:* Statelessness guarantees that no client state is retained in server memory between requests. This allows any server in a horizontally scaled cluster to process any incoming request, enabling seamless load balancing, high availability, and fault tolerance.
